# V1 operator and requirement contract

Status: implemented contract, last reviewed 2026-09-19.

This document owns the provider-neutral contract between the local Autonomous Development
control plane and an operator adapter such as the independent Feishu bridge. A provider message,
chat ID, or open ID is never stored in the core domain; the adapter maps those identities to the
durable `request_id` and sends only the normalized request body below.

## Requirement lifecycle

`DevelopmentRequest` is immutable input. Editing a requirement creates another request; it never
overwrites `normalized_requirement_text` or `content_sha256` in place.

```text
received -> analyzing -> ready -> running -> completed
                                      |-> rolled-back
                                      |-> failed
                                      |-> cancelled
             \-> needs-human --response--> ready
```

The request stores the source label, external reference digest, title, normalized text, content
digest, target ID, cycle ID, pending intervention ID, workflow attempt and active DBOS workflow
ID. The full requirement is persisted in the request row; event payloads contain IDs, digests and
bounded summaries only.

`RequirementAnalysis` is generated by a read-only Codex turn. Its bounded fields are summary,
requirement acceptance criteria, requested paths, expected behavior, risks, missing information,
ambiguity and validation expectations. Mechanical policy validation is authoritative. A path
outside the active objective mutation policy, a forbidden path, missing baseline/contract
recovery, or material ambiguity becomes `HumanIntervention`; the policy is never widened.

When analysis is actionable, the control plane creates one deterministic `ChangeProposal` with:

- `diagnosis_id = None`;
- the current serving release and active objective revision;
- objective acceptance criteria retained alongside requirement criteria;
- only validated requested paths as allowed paths;
- objective forbidden paths, changed-file budget, attempt budget and contract gates;
- a bounded change intent, not the full requirement document.

The existing `AutonomousIterationWorkflow` and `PostPromotionSoakWorkflow` remain the only
owners of implementation, verification, build, deployment, k6, canary, promotion, rollback,
soak and cleanup. `RequirementAutonomyWorkflow` only prepares the cycle, delegates to those
workflows and writes the terminal operator event.

## Local operator API

The API is mounted on the existing loopback control plane (`127.0.0.1:8765`) and is not a public
or LAN interface.

| Method | Path | Purpose |
|---|---|---|
| POST | `/v1/operator/requirements` | Submit an immutable normalized requirement; same ID/content is idempotent, conflicting content is `409`. |
| GET | `/v1/operator/requirements/{request_id}` | Read request state, cycle state, serving release and pending intervention summary. |
| POST | `/v1/operator/requirements/{request_id}/start` | Claim one workflow identity and return immediately; the DBOS workflow runs in the background. |
| POST | `/v1/operator/requirements/{request_id}/cancel` | Cancel only before an unsafe-to-cancel running cycle. |
| POST | `/v1/operator/interventions/{intervention_id}/responses` | Close an open intervention; replaying the same answer is safe, rewriting it is rejected. |
| GET | `/v1/operator/events?after=N&limit=M` | Read the durable monotonic outbox cursor. `limit` is bounded to 500. |
| POST | `/v1/operator/events/{event_id}/ack` | ACK after the adapter has successfully sent the notification. |

The JSON contract uses camelCase on the wire. A submit body is:

```json
{
  "requestId": "feishu:message-id",
  "targetId": "the-single-registered-target",
  "source": "feishu-autodev",
  "externalReferenceDigest": "sha256-of-provider-event-identity",
  "title": "bounded title",
  "normalizedRequirementText": "UTF-8 normalized text",
  "contentSha256": "64 lowercase hexadecimal characters"
}
```

The adapter must not send a requirement to the feedback endpoint. `UserFeedback` remains
untrusted runtime evidence; a human requirement enters this contract directly.

## HMAC transport

The bridge and control plane use a new, independent operator HMAC secret loaded from secret
files. It must not equal the old gateway notification HMAC, administrative HMAC, user HMAC,
control-plane key, or Feishu App Secret.

Every request includes:

- `X-Operator-Timestamp` (Unix seconds);
- `X-Operator-Signature` (lowercase HMAC-SHA256 hex);
- an endpoint-specific request/event identity bound into the signature.

The signed canonical bytes are:

```text
timestamp\nrequest-or-event-id\nUPPERCASE-METHOD\npath[?canonical-query]\nsha256(body-bytes)
```

The timestamp TTL is configurable and defaults to 300 seconds. Durable request IDs, immutable
content digests, workflow IDs, event IDs and ACK state make retries/replayed provider deliveries
idempotent; a reused identity with different content is rejected. The secret is never written to
logs, metrics, request bodies, event payloads or Git.

## Durable outbox

The application database owns `operator_events`. Important events are
`requirement_received`, `requirement_ready`, `development_started`, `needs_human`, `completed`,
`rolled_back`, `failed` and `cancelled`. Event sequence is monotonic. A bridge advances its own
cursor only after a successful provider send and an explicit ACK. A bridge outage therefore
delays notification but cannot fail or roll back the development workflow.

The control-plane `/ready` check includes operator HMAC configuration, database reachability,
pending event count, pending intervention count and latest event sequence. `/metrics` exposes
`operator_events_pending` and `interventions_pending` without provider identifiers or text.
